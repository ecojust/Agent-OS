# 第三方应用兼容性与验收

## 1. 产品要求

Agent OS 的系统目标包括：常用第三方 Android 应用安装后能够正常日常使用，Agent 功能不会破坏应用原有行为。本文件规定实现边界和发布验收，不表示已经通过测试；当前尚无已验证应用清单。

首版场景为**无实体 SIM 卡、无启用 eSIM，通过 Wi-Fi 使用**；蜂窝通话、短信、移动数据及专门来电中断流程不作为首版功能和测试要求。Wi-Fi 网络语音仍可能存在，其普通应用可用性按冻结流程记录，Agent 自动接听或处理来电不在首版范围。通用锁屏、窗口变化、用户接管和撤权保护仍适用，见[设计规则](DESIGN_RULES.md)。

必须分别记录三类结果：

| 维度 | 需要证明的结果 |
| --- | --- |
| 可安装与升级 | 正式安装包可安装、启动、更新，数据与签名校验符合平台规则 |
| 日常可用 | 用户能完成该应用的核心流程，例如登录、浏览、收发消息、播放或文件操作 |
| Agent 可操作 | 在用户授权范围内，Agent 能观察并完成明确任务，操作后有结果依据 |

应用不可被 Agent 读取或自动操作，不应影响用户手动使用。应用能启动也不等于登录、通知、支付、相机等功能均可用。

APK 执行器模式保留原厂系统的应用运行环境；完整系统镜像则必须承担 Android 运行时、系统服务和设备驱动的兼容责任。执行器的 `minSdk` 不决定其他应用能否安装，第三方应用自身的最低版本、ABI 和服务依赖需要单独满足。

## 2. 保留标准 Android 应用底座

优先使用所选 AOSP 版本的标准组件与公开接口，在系统交互层和受控服务边界增加 Agent 能力，避免为 Agent 修改第三方 APK 或普遍改写应用运行行为。

| 组件 | 兼容要求 |
| --- | --- |
| ART、核心类库 | 保持对应版本的应用执行、类加载、异常和垃圾回收语义，不替换为自建应用运行环境 |
| Bionic、JNI 与原生库 | 验证实际支持的 ABI、链接器行为与内存页大小；仅含 32 位库的应用在纯 64 位系统上不能假定可用 |
| 包管理与安装更新 | 保留安装器、签名、拆分 APK、升级及卸载规则；测试更新后数据与授权状态 |
| 权限、UID 与存储 | 保持应用沙箱、运行时权限、文件选择器、分区存储和 URI 授权行为 |
| Activity、Intent 与任务栈 | 验证启动、分享、文件打开、Deep Link、返回导航、多窗口和应用间跳转 |
| WebView | 配置可用、可维护的 WebView 提供方，验证嵌入网页、登录和网页文件上传；更新后执行回归 |
| 图形与媒体 | 验证图形驱动、硬件加速、音视频编解码、录制与播放、音频焦点及设备路由 |
| 通知与后台任务 | 保持通知、JobScheduler、闹钟和前台服务的标准行为，不为 Agent 全局关闭省电或杀进程策略 |
| 网络、定位与硬件 | 验证 DNS/TLS、Wi-Fi 切换、定位、相机、麦克风、蓝牙、传感器和设备声明的功能 |
| 电话组件与接口 | 保留标准 Android 电话组件及 API，按真实硬件声明能力；无 SIM 不意味着删除组件、伪造有卡状态或改变其他应用的标准调用行为 |
| 密钥与认证 | 验证 Keystore、生物识别和设备实际具备的安全能力，不伪造硬件能力或可信状态 |

应用声明的硬件能力应与真实设备一致；不能通过错误的系统特性声明让应用走向不可用的功能路径。模型服务、Agent 界面或执行器发生故障时，第三方应用仍应按正常 Android 生命周期运行。

## 3. 外部服务与认证边界

部分应用依赖 AOSP 之外的组件、商业授权或服务端判断，需作为实际兼容条件验证：

- **GMS 与相关服务**：不属于 AOSP，使用和分发涉及相应授权。需要这些服务的应用可能在纯 AOSP 环境中无法登录、推送或调用相关功能，不能因为系统通过基础测试便宣称可用。
- **设备完整性与应用风控**：启动链、Bootloader 状态、系统签名、认证与服务端策略可能影响金融、支付、游戏等应用。不得伪造完整性结果或承诺任意定制系统都能通过。
- **DRM 与受保护媒体**：可播放普通视频不等于具备受保护内容或高画质播放资格；需验证设备安全硬件、有效授权和应用实际播放结果。
- **厂商专有服务**：账号、推送、定位、穿戴连接等依赖需逐项登记。不能假设替换系统后仍有与原厂相同的服务能力。
- **手机号与本机 SIM 依赖**：允许人工使用合法测试账号，或按服务规则通过其他受控设备取得验证码后登录；这不能证明本机收发短信可用。必须依靠本机 SIM、运营商认证或本机收发短信才能完成的流程，不得在未满足依赖时记为通过，结果注明未验证或不支持及具体原因。

应用需要这些依赖时，先确定合法、可维护的提供方式再测试。无法满足的项目明确标为受限或不支持，并保留在应用清单和整体结果中；不以隐藏应用、修改 APK 或规避安全校验掩盖问题。

## 4. 应用样本与发布门槛

首轮建议建立**至少 50 个常用应用**的固定样本，覆盖通信与社交、浏览器、办公与文件、购物与出行、地图、金融支付、影音和游戏等类别。使用官方渠道或其他有权使用的正式安装包，记录来源、包名、版本、签名信息、地区和必要服务依赖。

测试开始前冻结样本、应用分类、关键必测名单与每个应用的核心流程。名单更新需要记录原因并保留上一版结果；失败、未知或依赖缺失的应用不能从原分母删除以提高通过率。

无卡范围及允许的人工登录方式在冻结前写入测试方案；冻结后发现本机 SIM 依赖，不能删除该应用、移出原分母或删减失败流程来提高通过率。完整样本结果保留该限制，发布说明明确仅覆盖实际验证的 Wi-Fi 流程。

以下为**设计目标与拟定发布门槛，尚未达到，也不代表市场应用总体覆盖率**：

| 指标 | 目标与统计口径 |
| --- | --- |
| 普通常用应用核心流程通过率 | 目标不低于 95%；分子为全部预设核心流程通过的普通样本数，分母为冻结的普通样本总数 |
| 关键必测应用 | 目标 100% 通过预设核心流程；未通过时不能将对应机型与系统组合标为满足日常使用验收 |
| 完整样本核心流程通过率 | 目标不低于 90%；分子为全部预设核心流程通过的应用数，分母为冻结的完整样本数，依赖缺失、失败及未验证项仍计入分母 |
| 完整样本结果 | 同时公布全部样本的通过、有限可用、失败和未验证数量；依赖认证或外部服务的应用仍留在整体结果中 |
| 有特殊依赖的子集 | 单独列出依赖、具体失败功能和结果，同时纳入完整样本汇总；不能只公布普通子集的高通过率 |
| Agent 操作通过率 | 与日常使用分开统计，明确模型、授权范围和任务；不能用 Agent 任务失败率替代应用兼容结论 |

应用只有安装成功或部分流程通过时不能计为完整通过；没有合法测试账号、服务不可访问或无法执行某个必测流程时，标为未验证。测试结果按具体机型、系统构建、应用版本和地区条件发布，不推广成整品牌或全部版本兼容。

上述门槛按每个发布机型、系统构建及服务配置分别计算，不能用跨机型平均通过率掩盖某个组合的失败。

## 5. 必测流程与状态

### 安装和日常功能

- 全新安装、首次启动、签名一致的正常更新、重启后再次使用；测试升级后的数据保留与权限状态。
- 合法测试账号登录与会话保持、网页登录回跳、输入法和必要的文件访问；记录人工验证码等外部依赖，不把借助其他设备登录当成本机短信能力通过。
- 消息或服务通知送达、通知点击、后台恢复，记录所依赖的推送方式与网络条件。
- 音视频播放、前后台音频、音频焦点、相机拍摄或扫码、麦克风与系统媒体选择器。
- 分享、文件打开、Deep Link、地图定位及应用间跳转，核对 URI 授权与实际结果。
- 横竖屏、键盘和导航方式、旋转后恢复、Wi-Fi 切换或断开、低内存与系统进程回收。
- 金融、支付及其他高影响流程使用合法测试环境并由人工接管确认；自动化验收不自行执行真实交易。

### Agent 对日常使用的影响

相同设备、应用、数据与网络条件下，分别验证：

1. **Agent 关闭**：没有 Agent 任务或执行观察，作为应用正常使用基线。
2. **Agent 已启用但空闲**：服务可用但未执行任务，检查通知、应用恢复、CPU、内存和耗电是否产生回归。
3. **Agent 正在执行**：在授权范围内完成测试任务，检查界面响应、输入、绘制、媒体、任务切换和停止后的恢复。

应用正常启动、登录、通知和核心流程不得因为 Agent 空闲而失效。执行状态下，悬浮控制不能截获无关输入、修改其他应用窗口行为或扩大权限；用户停止后，旧任务回调不能继续操作应用。

性能数据按[性能架构与验收预算](PERFORMANCE.md)验收，记录冷/热启动、帧时间、卡顿、ANR、CPU、内存、耗电和温升。对照相同系统中 Agent 关闭与开启的差异；系统镜像再增加与参考基线系统的对照。测试顺序、次数、温度、屏幕刷新率和缓存状态必须可复现，不能把网络或模型响应时间算作本机 UI 阻塞。

## 6. 平台测试与问题处理

系统镜像依照对应版本的 **CDD** 检查兼容要求，执行适用的 **CTS/CTS Verifier** 与 **VTS**，关注 Framework、应用 API 和厂商接口兼容性。记录测试版本、设备构建、适用范围、失败项与复测结果，不能将未运行或失败的项目标为通过。

无卡产品范围不豁免实际适用的平台兼容要求，也不能通过错误声明电话硬件能力规避套件测试；产品未验证的蜂窝功能不在发布说明中标为已通过。

平台套件通过后仍需执行上述真实应用流程。CTS/VTS 的通过不自动赋予 GMS 授权、DRM 等级或完整性服务认可，也不证明所有第三方应用的服务端策略均满足。

问题按以下顺序处理：先判断是平台/驱动、缺失依赖、应用版本要求、Agent 干扰还是应用自身问题；修复后重跑受影响流程及固定回归样本。兼容性修复不得破坏其他应用的标准 API 语义。临时规避应有明确机型与版本范围、回归测试和撤销条件，不采用全局常驻 Hook 改写第三方应用行为。

记录与设备分级沿用[兼容性策略](COMPATIBILITY.md)。发布前同时检查普通应用阈值、关键必测应用、完整样本汇总、平台测试结果和性能回归；不能只展示其中最有利的一个指标。
