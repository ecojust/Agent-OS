# 性能诊断采样

本轮提供实际运行时采样工具，尚未完成真机性能预算验收。工具记录原始 CPU、PSS、主线程排队／执行阶段及停止状态时点；不根据模拟器结果修改[性能预算](PERFORMANCE.md)，也不把诊断测试通过等同于预算达标。

## 测量范围

`PerformanceDiagnosticsInstrumentedTest` 在专用合成测试设备上依次执行：

| 阶段 | 实际行为 |
| --- | --- |
| A | Agent 无障碍服务关闭；应用及 instrumentation 进程仍驻留，前台为合成 fixture |
| B | 仅开启服务，无任务、控制条或主动观察；保持同一前台 fixture |
| C | 真正的 Controller 通过本地 HTTP 合成模型完成输入、保存、点击，逐次确认并通过真实观察验证 |
| STOP | 另一项合成任务停在确认阶段，通过主线程队列调用停止，检查本地状态发布及随后 500 ms 内没有新动作 |

A、B 各采样约 6 秒；C、STOP 按实际任务耗时采样。固定顺序用于首轮诊断，尚不是交替顺序、足量重复的配对基准。A 不是进程被强制停止的状态。C 与 STOP 的本地模型服务、instrumentation、采样器和原生应用位于同一进程；独立 fixture 和系统进程不计入当前 CPU/PSS。因此不能用 C−A 宣称完整 Agent 增量预算通过，也不能用这些数据代表真实网络与模型延迟。

测试不主动 GC，不修改系统动画。现有 CI 运行器另行统一系统动画为 1.0，其条件应与报告一起保存。每阶段截图通过 `ScreenshotEvidence` 在采样窗口之外实际获取，仍遵守敏感窗口限制。数值报告不是 UI 截图证据。

## 原始数值与阶段

- CPU：`Process.getElapsedCpuTime()` 的累计 CPU 毫秒与 `elapsedRealtimeNanos` 墙钟时点。两个样本间 `100 × ΔCPU毫秒 ÷ Δ墙钟毫秒` 表示单个逻辑核心占满为 100%；不除以核心数量。包含插桩、同进程模型及采样开销。
- 内存：每约 1 秒在非主线程执行 `Debug.getMemoryInfo()`，保存总 PSS 和 Dalvik／Native／Other PSS，单位 KiB。采样最大值不等于瞬时峰值，不把分项再次叠加到总量。
- 主线程：`MAIN_QUEUE` 记录从提交到回调开始的排队时间；`MAIN_CALLBACK` 记录实际回调时间。快照分别标明观察、准备、最终打开应用、最终写操作，并记录线程和节点／字节数量。排队阶段的线程字段表示提交线程。
- 停止：`STOP_RECEIVED` 是有效停止调用进入方法的时点，`STOP_EPOCH_INVALIDATED` 是本地取消生效时点，`STOP_UI_APPLIED` 仅在相同停止代次的非运行状态实际应用后标记。它是 UI 状态已应用，不是屏幕呈现时间；合成停止入队时点也不是物理触屏时点。空闲重复停止不产生有效样本。
- 快照阶段的 `mainThread` 字段用于识别实际执行路径；第十二轮报告仍为主线程，后续工作线程实现须以对应新运行报告验证。所有 revision、窗口、授权和 epoch 检查保留，不能以删除校验减少耗时。

生产启动默认不启用采集。启用后的数值记录器最多保留 4096 条固定枚举事件，超出时记录覆盖数；不接受界面文本、节点标识、URL、密钥或任意事件名称。测试每个阶段最多采样 128 次；采样或事件超限会使诊断用例失败，原始报告仍尽可能保留。

停止报告保留原始时点，另给出请求入队→方法进入、方法进入→取消生效、请求入队→本地 UI 状态应用三段纳秒耗时。主线程已经阻塞时，排队延迟会计入第一和第三段，不能用方法内取消很快代替完整响应。非停止阶段或必要事件缺失时记录 `-1`，不以零伪装即时完成，也不计算单次样本的 P95。

## 运行与归档

在已安装 fixture 的专用 Android 测试设备上，可通过现有 Gradle instrumentation 流程运行该类；常规 API 矩阵也会执行。测试输出到应用私有目录：

```text
files/performance/three-state-diagnostics.json
```

每次运行前清除旧报告；收集器将源码 SHA、CI 运行信息、实际 API 和采集状态与原始 JSON 一起归档。报告固定带有 `diagnosticOnly: true`、`budgetAcceptance: false`。`status: passed` 只说明合成任务、停止检查及数值采集通过。进程被终止、采样不完整、API 不匹配或报告校验失败必须保留为失败／未取得证据，不能复用旧结果。

真机验收仍需要固定机型与构建、真实应用流程、多批配对样本、完整帧耗时、相关进程资源及可靠峰值测量；这些项目不由本轮短窗口采样替代。

## 首轮结果与待定位项

[CI 40381396419 的八份报告](../screenshots/40381396419-1/performance/)均已采集、校验并归档。等待确认时的单次停止请求到本地 UI 状态应用为 6.511–32.867 ms；该阶段没有最终写前读取，不能证明繁忙读取期间的停止响应。

API 34、35、36 的最长最终写前快照分别为 185.431、182.103、141.189 ms，均在主线程；快照仅 12–13 个节点、约 4.2–4.5 KiB。前两项标记了截断，后续没有紧接派发，不能通过删除最后校验减少耗时。三个最长段均未与 PSS 采样窗口重叠，但墙钟记录仍无法区分 Binder 等待、调度、GC 与实际计算。

A/B 每档各 7 个样本，单次内存采集约 6.6–36.2 ms；C 仅约 0.45–1.55 秒、2–3 个样本。固定顺序、同进程采样和模型、服务初始化及自然内存回收都会影响结果，不能据此推断稳态开销或瞬时峰值。下一步应增加最终读取期间的停止回归，拆分窗口读取、树读取及序列化阶段，并结合系统 trace、采样开关对照、交替长窗口和真机测量定位。

## 工作线程与提交边界

完整的最终快照、节点使用、系统调用和节点回收在同一个串行工作线程执行，不将可回收节点交给排队中的 UI 回调。主线程仅提前提供稳定的不可变控制条位置凭据；布局、回调、拖动、连接变化使凭据失效。最终快照之后不再等待主线程，提交前同时检查凭据、原代次、窗口、界面版本及安装身份；不能取得新凭据后复用旧快照。

本地提交凭据只表示一个工作线程进入提交阶段，不表示系统已接受。停止使原代次失效并阻止新凭据，调用前再次检查已观察到的取消；已经进入提交阶段的动作可能仍在返回，结果未知时不得自动重发。票据及进程级设备通道都由原工作线程在 `finally` 中释放，停止或服务重建不能提前释放，也不等待远端 Binder 调用。

无障碍查询通过每个调用线程的交互客户端访问目标应用；目标应用处理动作仍发生在其自身 UI 线程。底层查询可能等待远端响应且不立即响应 Java 中断，因此本轮目标是保持本机控制界面响应，不能承诺底层调用即时撤回。实现依据见 [交互客户端源码](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/accessibility/AccessibilityInteractionClient.java)与[节点动作接口](https://developer.android.com/reference/android/view/accessibility/AccessibilityNodeInfo#performAction(int))。Android 11/12 的缓存配置刷新仍保持单工作线程所有权，不与其他设备请求并发修改服务配置。

[第十三轮原始报告](../screenshots/40386701414-1/performance/)已验证 25 次最终写前快照及 24 次派发记录均在工作线程。C 阶段设备主线程回调最大值为 0.744–4.217 ms，UI 发布回调最高 11.491 ms；后者不能被遗漏。API 37 仍记录到 184.232 ms 的工作线程快照并截断。停止请求到状态应用为 17.755–42.612 ms，仍只覆盖等待确认时的单次样本；A/B 事件记录为零，无最终打开应用的数值样本。本轮与上一轮没有固定相同 CI 主机，不能将这些观察值当作严格配对的加速比例。完整矩阵有一项 API 35 遮挡失败，性能诊断通过不覆盖该失败。


[第十四轮原始报告](../screenshots/40389290084-1/performance/)继续取得八份有效诊断：24 次最终写前快照及 24 次派发均在工作线程，最终快照各档最大值为 7.236–40.604 ms，本轮这些快照未截断。C 阶段设备主线程回调各档最大值为 0.484–6.235 ms，另有 UI 发布回调 14.286 ms、主线程排队 19.292 ms，不能遗漏后两类开销。等待确认时的单次停止请求到 UI 应用为 5.171–26.814 ms，仍非繁忙场景或 P95；A/B 各 7 个样本且无执行事件，仍无最终启动应用的数值覆盖。整体设备矩阵为 335/336，API 36 遮挡暂停失败不被性能采集通过覆盖。本轮与此前运行不是同机配对，较小的查询数值不能用来宣称固定加速比例或真机预算已达标。


[第十五轮原始报告](../screenshots/40391925593-1/performance/)随完整 336 项设备回归通过归档。25 次最终写前快照与 24 次动作提交尝试全部位于工作线程；设备主线程回调最大 7.725 ms、UI 发布最大 19.233 ms、主线程排队最大 18.959 ms。API 37 的最终快照仍有 186.255 ms 截断样本，API 36 的普通观察有 186.869 ms 截断样本，均在工作线程；额外最终快照没有对应额外提交。不能把没有占用主线程等同于查询尾延迟已消除。

八个等待确认场景的单次停止请求到 UI 状态应用为 5.426–38.785 ms，三时点和计算结果逐一吻合，均没有随后派发。A/B 各 7 个样本且无执行事件，C/STOP 各 2 个样本，记录器无覆盖丢失；最终启动应用仍无计时覆盖。这轮没有真机或足量重复样本，不计算 P95，也不宣称预算验收或跨 CI 运行的严格配对提速。

## 第十八轮对照与内存待测项

[第十八轮八份原始报告](../screenshots/40401644646-1/performance/)随 520 项设备回归通过归档。25 次最终写前快照和 24 次提交尝试仍全部在工作线程；设备主线程回调最大 4.144 ms、UI 发布 9.290 ms、主线程排队 19.729 ms。等待确认时的单次停止请求到 UI 状态应用为 9.977–30.838 ms。API 34 的最终快照 185.673 ms、API 35 的准备快照 184.917 ms 均在工作线程并被截断，查询长尾仍未消除。

与第十五轮相比，报告中的 API、设备描述和采样条件一致；A/B 各七个样本，C/STOP 通常各两个，第十八轮 API 34 的 C 有三个。不同 CI 主机、固定阶段顺序和少量样本不构成严格配对基准，不能将最大值差异解释为确定的提速，也不计算 P95。

第十八轮 A 阶段总 PSS 的各档中位数为 60.84–72.98 MiB，比第十五轮高 1.67–17.42 MiB；API 33、35 分别高 17.42、15.11 MiB，Native PSS 分别约高 9.19、10.03 MiB。所有环境在这次采样前都已执行新增的图片审阅测试，旧轮没有这些用例，界面初始化、位图分配与分配器保留都会影响后续驻留值。这是待解释的观测，尚不足以认定泄漏或将差值当作新增功能的净内存成本。

本轮 B−A 的 PSS 中位数差为 −0.04 至 +0.09 MiB，A/B 无执行事件，区间 CPU 单核等效约 0.915%–1.694%；没有从这组短窗口样本发现新增的空闲执行循环。后续应在新进程中独立运行基准，并重复打开、关闭审阅界面观察内存趋势，同时记录峰值和相关进程，不能用当前数据代替性能预算验收。
