# 性能诊断采样

本轮提供实际运行时采样工具，尚未完成真机性能预算验收。工具记录原始 CPU、PSS、主线程排队／执行阶段及停止状态时点；不根据模拟器结果修改[性能预算](PERFORMANCE.md)，也不把诊断测试通过等同于预算达标。

## 测量范围

`PerformanceDiagnosticsInstrumentedTest` 在专用合成测试设备上依次执行：

| 阶段 | 实际行为 |
| --- | --- |
| A | Agent 无障碍服务关闭；应用及 instrumentation 进程仍驻留，前台为合成 fixture |
| B | 仅开启服务，无任务、控制条或主动观察；保持同一前台 fixture |
| C | 真正的 Controller 通过本地 HTTP 合成模型完成输入、保存、点击，逐次确认并通过真实观察验证 |
| STOP | 另一项合成任务停在确认阶段，通过主线程队列调用停止，检查本地状态发布及随后 500 ms 内没有新动作 |

A、B 各采样约 6 秒；C、STOP 按实际任务耗时采样。固定顺序用于首轮诊断，尚不是交替顺序、足量重复的配对基准。A 不是进程被强制停止的状态。C 与 STOP 的本地模型服务、instrumentation、采样器和原生应用位于同一进程；独立 fixture 和系统进程不计入当前 CPU/PSS。因此不能用 C−A 宣称完整 Agent 增量预算通过，也不能用这些数据代表真实网络与模型延迟。

测试不主动 GC，不修改系统动画。现有 CI 运行器另行统一系统动画为 1.0，其条件应与报告一起保存。每阶段截图通过 `ScreenshotEvidence` 在采样窗口之外实际获取，仍遵守敏感窗口限制。数值报告不是 UI 截图证据。

## 原始数值与阶段

- CPU：`Process.getElapsedCpuTime()` 的累计 CPU 毫秒与 `elapsedRealtimeNanos` 墙钟时点。两个样本间 `100 × ΔCPU毫秒 ÷ Δ墙钟毫秒` 表示单个逻辑核心占满为 100%；不除以核心数量。包含插桩、同进程模型及采样开销。
- 内存：每约 1 秒在非主线程执行 `Debug.getMemoryInfo()`，保存总 PSS 和 Dalvik／Native／Other PSS，单位 KiB。采样最大值不等于瞬时峰值，不把分项再次叠加到总量。
- 主线程：`MAIN_QUEUE` 记录从提交到回调开始的排队时间；`MAIN_CALLBACK` 记录实际回调时间。快照分别标明观察、准备、最终打开应用、最终写操作，并记录线程和节点／字节数量。排队阶段的线程字段表示提交线程。
- 停止：`STOP_RECEIVED` 是有效停止调用进入方法的时点，`STOP_EPOCH_INVALIDATED` 是本地取消生效时点，`STOP_UI_APPLIED` 仅在相同停止代次的非运行状态实际应用后标记。它是 UI 状态已应用，不是屏幕呈现时间；合成停止入队时点也不是物理触屏时点。空闲重复停止不产生有效样本。
- 当前最终写前快照依然在主线程执行，所有 revision、窗口、授权和 epoch 检查均保留。该路径的潜在耗时在报告中可见，本轮没有宣称已解决。

生产启动默认不启用采集。启用后的数值记录器最多保留 4096 条固定枚举事件，超出时记录覆盖数；不接受界面文本、节点标识、URL、密钥或任意事件名称。测试每个阶段最多采样 128 次；采样或事件超限会使诊断用例失败，原始报告仍尽可能保留。

停止报告保留原始时点，另给出请求入队→方法进入、方法进入→取消生效、请求入队→本地 UI 状态应用三段纳秒耗时。主线程已经阻塞时，排队延迟会计入第一和第三段，不能用方法内取消很快代替完整响应。非停止阶段或必要事件缺失时记录 `-1`，不以零伪装即时完成，也不计算单次样本的 P95。

## 运行与归档

在已安装 fixture 的专用 Android 测试设备上，可通过现有 Gradle instrumentation 流程运行该类；常规 API 矩阵也会执行。测试输出到应用私有目录：

```text
files/performance/three-state-diagnostics.json
```

每次运行前清除旧报告；收集器将源码 SHA、CI 运行信息、实际 API 和采集状态与原始 JSON 一起归档。报告固定带有 `diagnosticOnly: true`、`budgetAcceptance: false`。`status: passed` 只说明合成任务、停止检查及数值采集通过。进程被终止、采样不完整、API 不匹配或报告校验失败必须保留为失败／未取得证据，不能复用旧结果。

真机验收仍需要固定机型与构建、真实应用流程、多批配对样本、完整帧耗时、相关进程资源及可靠峰值测量；这些项目不由本轮短窗口采样替代。

## 首轮结果与待定位项

[CI 40381396419 的八份报告](../screenshots/40381396419-1/performance/)均已采集、校验并归档。等待确认时的单次停止请求到本地 UI 状态应用为 6.511–32.867 ms；该阶段没有最终写前读取，不能证明繁忙读取期间的停止响应。

API 34、35、36 的最长最终写前快照分别为 185.431、182.103、141.189 ms，均在主线程；快照仅 12–13 个节点、约 4.2–4.5 KiB。前两项标记了截断，后续没有紧接派发，不能通过删除最后校验减少耗时。三个最长段均未与 PSS 采样窗口重叠，但墙钟记录仍无法区分 Binder 等待、调度、GC 与实际计算。

A/B 每档各 7 个样本，单次内存采集约 6.6–36.2 ms；C 仅约 0.45–1.55 秒、2–3 个样本。固定顺序、同进程采样和模型、服务初始化及自然内存回收都会影响结果，不能据此推断稳态开销或瞬时峰值。下一步应增加最终读取期间的停止回归，拆分窗口读取、树读取及序列化阶段，并结合系统 trace、采样开关对照、交替长窗口和真机测量定位。
