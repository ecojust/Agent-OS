# 开发签名 APK 原地升级验证

本模块落实[R9 更新与恢复](../DESIGN_RULES.md#r9-更新迁移与恢复)的一项独立验证：使用真实产品源码构建的两份开发 APK，在专用合成模拟器执行一次正常原地升级，检查配置、Keystore 和原有应用授权是否连续。当前先声明测试合同；构建、脚本与设备实际结果在取得后分别记录。

## 固定产物与分母

- 旧版本固定为源码 `b1fd337262775a505327088975a3320fe323f034`，实际 `versionCode=1`、`versionName=0.1.0`。
- 候选版本来自本次工作流的精确源码，实际 `versionCode=2`、`versionName=0.1.1`。配置格式保持原版本，没有虚构一次数据格式迁移。
- 两份 APK 分别从对应源码构建，不修改已生成 APK 的清单。一次构建任务生成临时开发签名身份，两包使用同一身份；可信证书摘要从该密钥库导出的公开证书独立取得，再用已有[离线预检](apk-upgrade-preflight.md)检查确切产物。私钥不归档。
- API30、31、32、33、34、35、36、37.0，共八个固定组合。每个组合包含升级前准备与升级后验证两个阶段，不能将两个阶段算成两个独立通过案例。失败和未运行保留在八项分母中。
- `upgrade-smoke` 是独立测试模块，不加入原应用完整仪器回归的270项/API。此前2160/2160结果仍绑定原24b9源码，不自动改标成新版本结果。

## 一次正常更新的合同

1. 驱动核实专用全新模拟器、实际API和设备身份，确认目标包未安装；只在该环境安装旧 APK、固定合成 Fixture 与独立探针。
2. 升级前通过真实默认 `SettingsStore` 保存合成连接、四项数值、执行模式及 Fixture 授权。配置使用正常Keystore加密路径；不通过外部写入数据库或复制配置来制造保存结果。
3. 使用本地测试模型启动受控任务，观察到待确认后明确停止，确认没有派发写操作并等待原工作退出。任务不获批准；停止后记录配置摘要和真实读取结果。
4. 结束第一阶段，重新打开旧版本普通入口并记录实际进程。仅执行一次 `adb install -r` 安装候选，不卸载、不清数据、不降级、不自动重装或重放失败更新。
5. 核对设备实际安装包与已检查产物一致，版本递增，UID及首次安装时间连续；新进程先读取原配置，不能先保存、重置或重新捕获授权来补足丢失数据。
6. 新进程必须真实解密，并核对全部固定字段、密文与配置revision摘要、原资料及原授权。使用原授权重新检查Fixture安装身份；授权记录存在不等于授权仍有效。
7. 在升级后的独立验证进程中核对旧任务、待确认动作和内存结果没有恢复。升级前原任务的派发计数必须为零；候选控制器没有任务owner、工作队列保持空闲，宿主在本次观察期间没有收到新增模型请求。这不是全局设备输入计数。主界面维持安全窗口，候选入口的任务输入为空；本轮没有种入旧编辑草稿，不能据此验收草稿跨升级恢复规则。

测试记录采用固定布尔值、计数和摘要，不导出密钥、原配置、页面正文或完整网络内容。此处“新进程”只证明进程边界；任务在更新前已经显式停止，不将其称作安装器中断在途任务的验证。

## 证据与限制

工作流为[apk-upgrade-smoke.yml](../../.github/workflows/apk-upgrade-smoke.yml)。`mode=test` 构建固定产物并运行八档；完成后以同一工作流的 `mode=archive` 归档到 `screenshots/apk-upgrade-<run>-<attempt>/`。归档核对源码、运行轮次、产物身份、原阶段回执和文件校验值；成功归档本身不表示测试通过。

配置界面保持 `FLAG_SECURE`，采集记录明确为受保护、不尝试截图；不清安全标记或生成替代图片。整体演示另用既有普通合成应用流程录制，准确标记源码并保持视频小于100 MB；它不替代受保护配置及安装更新的验收。录制失败保留失败记录，不阻塞功能提交。

这一合同只覆盖同一配置格式、一次开发签名升级和受控停止后的行为。正式签名与轮换、未知配置格式、真实格式迁移、在途外部替换、降级、进程死亡恢复、实体手机、ROM/OTA、广泛第三方应用及性能预算仍分别待验收。Notes v4的24/32和八项失败保持原记录，不由本模块替代。
