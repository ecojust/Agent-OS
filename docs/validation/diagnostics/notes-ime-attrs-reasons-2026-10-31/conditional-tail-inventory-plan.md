# 条件方案：独立解析主窗口和尾部记录

此文仅是待评审设计，未实施或采用。只有新一轮的原件支持 `ATTRS_ANCHOR_DUPLICATE`、最后主记录及已知尾部标题位于两个属性锚点之间等结构时，才考虑另一个冻结源码的解析修正；否则继续按实测原因调查。不能把这份设计当作本轮根因、原应用失败修复或旧记录的重算结果。

## 范围和版本差异

仍只处理原来一条完整返回的 `dumpsys -t 2 window -a windows`，不增加命令、动作、截图权限或原v4预算。新候选解析需显式记录自己的清单范围/版本，旧源码的 `WMS_ATTRIBUTES_INCOMPLETE` 和 null匹配保留。

固定16/17源码均先打印 `Window #N` 主记录，再可能打印 Hiding、Removing、Destroy、Resizing 四类尾部完整记录。12L还存在 `Remove pending for:` / `Remove #N`，也会调用 `WindowState.dump`。因此跨版本方案必须显式支持这一分支或遇到它即不可用，不能把“四类”称为全部尾部。Waiting-for-drawn节只提供窗口引用，不能直接当作一份完整属性记录。

[16r1源码记录](aosp16-wms-record-boundaries.md)和[补充固定源码索引](tail-design-source-index.json)分别保存依据。公开源码不证明实测镜像完全相同。

## 最小解析步骤

1. **显式分段。** 主记录、已知尾部节、该节内条目以及全局字段起点分别识别。主头为 `Window #N`；尾部条目只在其已识别节内接受相应 `#N` / `Removing #N` / `Destroy #N` / `Resizing #N` / `Remove #N`。以源代码规定的行首和缩进识别边界，不能只搜索任意名字中的关键词。每个锚定的mAttrs必须且只能归属一个完整记录。未知节、额外未归属属性、半条目、缺失/矛盾边界继续不可用；遇到未知结构不得直接截掉尾部。
2. **逐记录原规则解析。** 每份记录单独沿用8192字符、深度8、唯一顶层ty等界限；提取固定WindowState文本键、user、mClient、display、owner UID、package和type。类型只规范化已有明确别名，不扩展对未知类型的接受。无法完整解释的记录继续未知，不保存名字或原文。
3. **先检查冲突，再合并重复。** 同WindowState文本键或同mClient的多次出现，必须在另一对象键及上述固定身份字段上一致；双方都有的保留WMS状态字段也必须一致，缺失/重复/矛盾不能借另一份填补。不同对象键不能仅凭包名/标题/矩形合并。保留各出现位置和重复计数，实际比较仍是同一dump内的文本一致性，不是Binder强引用证明。
4. **尾部额外窗口进入核对集合。** 主清单没有但身份/类型完整的尾部窗口，不能丢弃；另一个IME、身份冲突或未知记录会使唯一候选不可用。最小方案仍要求被选中的配置IME出现在主清单，并与唯一 `mInputMethodWindow` 引用一致；仅存在于清理尾部的IME不作为当前候选。Waiting-for-drawn等纯引用若不能无歧义核对到已完整解析的记录，亦保持不可用。
5. **报告实际范围。** 输出主记录数、各尾部出现数、重复数、尾部新增窗口数、未知/冲突数及集合内IME数，明确为“主清单与支持的尾部记录中的文本候选”。不得把主清单范围冒充全局唯一窗口，也不得凭这个候选放行原BACK、确认或截图。

保持原字节/时间/16KiB标记边界；新条目明细另设固定保留上限并记录omittedCount。上限或序列化失败沿用明确不可用/回退，不扩大到无界记录。若边界解析必须扩展到未知服务输出，先保存不可用结果，再单独评审。

## 需要的验证

固定源码形状至少覆盖：无尾部、四类尾部、12L Remove-pending、同身份一致重复、同WindowState不同mClient、同mClient不同WindowState、固定字段/状态冲突、主清单外非IME和第二IME、未知条目/属性、纯引用无法核对、标题伪造边界、截断与超限。没有尾部的既有合法样本应保持候选结果；原来因重复尾部拒绝的样本只有在完整记录和冲突检查通过后才改变诊断结果。

实现和宿主验证通过后再冻结源码并预声明独立设备验证。原32项v4方法、失败分母及应用验收状态保持；新旧诊断运行分别报告。该方案只可能修复诊断范围的解析，不能称为输入法隐藏失败已修复。
