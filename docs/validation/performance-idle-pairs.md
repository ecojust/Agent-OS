# 同设备空闲 A/B 交替配对诊断

本模块补齐此前固定 A→B 顺序的测量缺口。专项仅测同一专用模拟器中服务关闭与连接空闲时的进程资源，报告始终为 `diagnosticOnly=true`、`budgetAcceptance=false`。真实设备结果和数值将在完成采集、归档与独立复算后补入；目前不据实现代码宣称已测得性能结论。

## 冻结的采集合同

- 同一测试进程、同一静态 Fixture 前台，开始时启动/重置一次，之后不重置应用数据；不启动模型、任务或控制条。
- 固定6对顺序：`AB / BA / AB / BA / AB / BA`，每对两个20秒窗口。每窗在服务状态就绪后固定等待2秒；状态切换、等待、前后检查及截图均在资源采样窗口之外。
- A 为 `A_SERVICE_OFF_RESIDENT_PROCESS`，服务关闭但仪器进程仍驻留；B 为 `B_SERVICE_ON_IDLE`，服务已连接且无任务。A不是卸载、进程终止或冷启动基线。
- 每秒采集当前进程累计 CPU 时间和 PSS，保存每次采样的单调时间与采集耗时。窗口前后核对服务、控制器、控制条及 Fixture 前台，两个状态的执行trace都必须为空。
- 每窗最多128个样本、4096个trace事件，报告最多2 MiB；丢样本、trace覆盖、服务状态不符或前台变化不能记为通过。失败保留已执行前缀与原结果，不追加窗口替换。
- 最后恢复原无障碍服务列表及启用状态。产品安全窗口保持启用；整个序列开始/结束截图，不在每窗之间截图，不关闭动画、不强制GC。

固定专项 `idle-pair-diagnostic` 在 API30、31、32、33、34、35、36、37.0 各执行一个仪器用例。计划分母为 **8案、96窗口、48对**，独立于当前273项/API完整矩阵。新探针明确从full选择中排除，专项结果不得改判上一轮矩阵的旋转失败。

## 证据和统计

设备原始文件为 `files/performance/idle-paired-diagnostics.json`。独立采集器验证schema、固定顺序、时间、样本及状态，绑定精确源码、run/attempt、API与CI profile；专项归档保留单独的 `idlePairedPerformance` 字段和 `idle-paired-performance/api-*/` 文件，不复用或改写旧四态报告。

CPU按每窗首末累计CPU差除以实际采样时间跨度，单个逻辑核心占满为100%；PSS记录实际采样的算术均值与采到的最大值。每对先计算 B−A CPU百分点及均值PSS差，再分别报告各API全部对、AB顺序和BA顺序的min/median/max。不同API不合成一个预算结论，失败、未执行和缺失项保持在48对计划分母中，不补零、不删样本、不报告P95/P99。

该实验只有状态顺序交替，没有控制所有缓存、宿主负载与热状态。BA中的A可能含服务断开后的残留资源，2秒等待不能证明资源完全回收；进程内仪器、采样器及逐窗保留的JSON/采样记录开销包含在测量中，Fixture进程不包含。20秒是每窗最低墙钟时长，CPU分母仍使用实际首末采样跨度。前后状态检查和有限trace不能证明窗口中每一瞬间都没有外部变化或所有可能的后台工作。数值用于诊断，不是服务自身净开销、完整应用体验或真机预算达标证明。
