# 多轮三态性能诊断汇总

`scripts/summarize_performance_runs.py` 将已归档的多轮八档性能附件整理成可复查的 JSON：保留每轮资源采样、原完整运行和作业结论，按相同 API、系统指纹、设备字段、CI profile 与采样条件分组，输出每轮三态数值、B−A/C−A 差值和跨轮 min/median/max。

它推进[性能检查点](../PERFORMANCE.md)的重复测量统计部分，不执行手机操作，也不重新运行或筛选设备测试。固定顺序的短时模拟器数据不能验收交替配对、持续压力、应用启动/完整帧、瞬时内存峰值、真实触摸、电耗、温升或真机预算。输出始终为 `diagnosticOnly=true`、`budgetAcceptance=false`。

## 使用

工具接受 **2–32 个不同运行**的完整归档目录，并要求显式指定共同的测试源码。下面使用已有的两份同源归档，输出需是尚不存在的新文件：

```bash
python3 scripts/summarize_performance_runs.py \
  --source 8e8e00518b11f55cca4c7c24dd74c49a0e35cd21 \
  --output /tmp/agent-performance-summary.json \
  screenshots/40975741234-1 screenshots/40975743980-1
```

省略 `--output` 时向标准输出打印 JSON。工具拒绝覆盖已有输出、在输入证据目录内创建输出，以及包含 `..` 或符号链接的输入/输出路径。生成失败不修改任何原始归档。同一 run 即使 attempt 不同，也不能当作两轮独立样本。

退出码：`0` 为性能诊断记录齐备；`1` 为有明确的缺失、未采集或失败诊断，仍写出包含这些条目的不完整报告；`2` 为输入身份、结构、摘要或输出路径不可信，拒绝生成报告。`status=complete` 只表示所有 API/run 的诊断报告可纳入统计，不代表完整功能运行通过、所有指标均有值或性能预算达标。

## 来源与文件核验

工具要求完整八档 API30、31、32、33、34、35、36、37.0 的归档结构，并检查：

- 原归档的仓库、master 分支、run/attempt、源码及运行链接与显式输入相符；原完整运行的失败结论原样保留。
- 顶层 manifest 的性能文件集合、大小及 SHA-256 与磁盘一致；capture 中的原运行身份、API、profile、采集状态与顶层对应。
- capture 指向的报告大小、摘要、状态再次与报告对应，并复用原 `collect_performance_evidence.validate_report` 验证四阶段、采样时序、原始数值、停止事件及空闲零派发等合同。
- 不混合不同源码；未知 CI profile 沿用原采集器的严格拒绝规则。不同系统指纹或其他设备字段分别建组，只有一个 run 的组明确为 `repeatedGroup=false`。

校验范围是本地已归档性能附件的身份及摘要链，不会重新认证 GitHub 上传时间或下载原 JUnit XML，也不重新审计 UI 截图或完整功能矩阵。来源应采用已完成归档审计的受信任仓库提交。报告记录输入 manifest 摘要、capture/report 摘要、原始文件相对位置，以及汇总脚本和报告验证脚本各自的 SHA-256；工具版本与被测 APK 源码分开记录。

完整运行失败但其中性能子案通过时，该有效性能数据可以进入描述性统计，同时保留 `fullRunConclusion=failure` 与原 job 结论。性能诊断失败或不可用则留在 `lanes` 中，记录排除原因和原报告位置，不补零、不删除、不用另一轮替换；`expectedLaneCount` 始终是输入轮数乘八。坏摘要、缺失 API 条目、矛盾来源等结构错误直接拒绝，不能通过排除样本掩盖证据问题。

## 统计口径

| 输出 | 定义及限制 |
| --- | --- |
| `wallMillis` | 该阶段开始至结束时长；与实际采样覆盖时间分别记录 |
| `resourceSampleSpanMillis` | 最后与最初资源采样时间差；不会把未采到的首尾间隔补入CPU分母 |
| `cpuPercentOneCore` | 首末 `processCpuMillis` 差除以首末单调采样时间差，换算为占满一个逻辑核心100% |
| `sampleMean*PssKiB` | 实际采样点的算术平均，不是按时间加权的常驻均值 |
| `sampleMax*PssKiB` | 采到的最大值，不能代表两次采样之间的瞬时峰值 |
| `sampleCollectionMaxMillis` | 本阶段采样调用耗时的最大值，采样器自身开销仍包含在进程CPU内 |
| `stopMillis` | 原始报告已验证的请求→方法进入、方法进入→代次失效、请求→UI状态应用时间；不含物理触摸与完整绘制 |
| `B_MINUS_A` / `C_MINUS_A` | 先在同一run内计算CPU百分点和PSS KiB差值，再对各run差值计算分布；保留负值 |
| 每组 `count/missing/min/median/max` | 每run等权的描述性分布，不池化不同阶段或不同run的原采样点，不计算P95/P99或置信区间 |

只有一个采样点或采样时间跨度为零时，CPU 为 `null`，并记录 `insufficient_sample_span`；相应 CPU 差值也为 `null`，分布的 `missing` 会增加，不能把该值当0。PSS仍保留实际单点数据。各阶段保留原 `resourceSamples`，便于重算。

所有现有报告的顺序均为 `A_B_C_STOP`。A 是服务关闭但进程仍驻留的仪器环境；B 是服务绑定空闲；C 是固定本地模型的合成任务，并非A里等价的手动任务。A/B约六秒，C/STOP通常更短，不能通过简单差值消除顺序、缓存和工作量差异。采样器与同进程本地模型计入开销，Fixture进程不计入；同组也没有控制未记录的宿主负载、热状态等条件。负差值不能解释为开启Agent节省资源。

## 验证

新增宿主回归覆盖已知手算数值、按run差值后汇总、单点CPU缺失、不同指纹分组、失败/缺失分母、重复run/attempt、source/API/profile与摘要链矛盾、非法报告、重复JSON键、路径穿越、符号链接及禁止覆盖输入/输出。已有性能采集/归档测试仍独立运行。

真实两轮 `8e8e00518` 归档已作为工具解析与计算交叉验证：16份性能子案均可纳入八个API分组；这两轮完整功能运行实际各2166/2168，报告保留 `failure`，不会被性能子案的通过覆盖。此处是工具验证范围，不新增设备验收结论。

后续仍需真正采集交替配对顺序、长时任务、目标应用进程和启动/完整帧数据，并在参考机上验证预算。本工具只使用当前附件已有指标，不生成未测量数据。
