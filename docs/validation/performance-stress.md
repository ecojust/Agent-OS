# 30分钟分段任务与服务启停压力

本任务在专用模拟器上执行固定的任务、停止及服务启停循环，观察资源变化并保存每段结果。八档专项与原始证据核验均已完成，实际结果见下文。它属于[性能后续任务](../PERFORMANCE.md#性能后续任务)，现有已完成的性能诊断检查点保持原验收范围。

## 固定验收范围

源码提交后使用独立 `stress-diagnostic` 专项，在API30、31、32、33、34、35、36、37.0各执行一项测试。每API固定30段，共 **240段、480个计划任务**：240个正常完成任务和240个在待确认状态下停止的任务。原273项/API完整矩阵明确排除此类，未重跑的历史矩阵保持原结果。

每段顺序如下，首个失败即结束，不能追加或替换失败段：

1. 新建Fixture、本地测试模型与实际保存配置，执行一次SAVE_AND_COUNT任务；三个写操作均需明确确认，核对产品终态及结果码MODEL_REPORT、模型收到的三次接受写入、实际保存值与Count1。测试核对不改变产品的“模型报告待核对”状态。
2. 使用新的Fixture和模型准备一个点击任务，等到进入待确认状态后停止。核对STOPPED/TASK_STOPPED、实际Count0、零接受写入、停止trace零派发，以及唯一的停止进入、代次失效和UI状态应用事件。
3. 清理控制器、模型与配置，等待服务断开，观察至少10秒恢复窗口。前后核对服务关闭、无运行任务/控制条及Fixture前台；恢复trace须为空。

每段至少60秒；上述工作较慢时记录实际超过60秒的时长，恢复窗口不能被缩短来凑时长。通过要求30段全部通过、各段测量时长总和及整体跨度均至少1800秒。它是带任务、启停和恢复间隔的30分钟场景，不是30分钟CPU饱和负载，也不证明全机没有ANR或泄漏。

## 分段采样与原始证据

每段每5秒采集当前进程累计CPU及PSS，另有开始/结束采样，最多128点；通过段需至少10点、首末采样跨度至少55秒。按实际采样跨度计算CPU；采样标签只是采集开始时观察到的阶段，不能当作原子任务状态。仪器、采样器、本地模型及当前段记录开销计入当前进程，Fixture和系统其他进程不包含。

正常任务、停止任务、服务关闭恢复分别使用有界trace，避免将正常任务的合法派发误判为停止后的派发。每段结束独立写入 `segment-000.json` 至 `segment-029.json`，再原子更新 `stress-diagnostics.json` 的小型来源引用；不在进程中累计全部30段JSON。每段至多4MiB，根清单64KiB，单API附件128MiB，仓库整体归档仍受64MiB上限约束。

开始时即写`incomplete`根清单，完成每段后更新已提交前缀。正常捕获的失败记录为`failed`并保留后续未执行项；进程被终止时，`incomplete`只证明已提交前缀，后缀可能已部分执行，记为未取得证据而不是未执行。采集器只取根清单引用的已提交文件，未提交临时文件或孤立文件不被当作成功段。

采集器按固定文件名、长度、摘要、顺序、时间、阶段结果及原始trace进行校验，所有ADB读取合计至多60秒。工作流、源码、API、attempt、原作业和附件上传时间由归档路径核验；旧四态/空闲配对合同独立保留。

## 执行与恢复

仅本专项默认40分钟外层执行上限，CI作业55分钟；其他scope保持20分钟执行与35分钟CI上限。探针在约35分钟整体期限内结束，具体平台同步调用仍受其既有等待及外层watchdog约束；不提高生产任务预算，不重放未知写操作。

外层恢复原无障碍服务列表及启用设置；每个任务单独清理Controller、Harness、本地服务器和临时配置。报告中恢复成功表示相应设置写入/清理已返回，不等于持续监控所有手机状态。保留原动画与安全窗口，不强制GC。截图只在整个序列前后及失败结束时取得，数值以原始报告为准。

## 统计与后续范围

汇总始终保留八档240段/480任务分母、原运行/作业/Gradle结果，以及失败、未执行、未取得证据。报告每段CPU、PSS采样均值/最大值及恢复采样，分别展示各API首末段变化与描述性分布。不同段不被当作独立设备，未采到的瞬时峰值或进程外开销不补算；资源首末差不能直接证明泄漏、因果效果或预算达标。

整体依旧为`diagnosticOnly=true`、`budgetAcceptance=false`。活跃等价人工对照、目标进程、启动TTID/完整帧、繁忙系统调用停止及真机功耗温升仍各自待验收。
